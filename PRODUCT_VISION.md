# Product Vision

## What Rostr Is

Rostr is a sports team operating system built for coaches, evaluators, and program administrators. It digitizes the operational workflows that run youth, high school, and club sports programs — tryout evaluations, roster management, practice planning, game-day preparation, and player development tracking.

Rostr produces verified athlete performance profiles backed by real evaluation data entered by credentialed coaches, not self-reported stats.

## What Rostr Is Not

Rostr is not a social media platform for athletes. It is not a highlight reel service. It is not a messaging app. It is not a generic sports statistics website. It is not a recruiting marketplace (yet). It does not replace coaching judgment — it gives coaches better tools to organize, record, and communicate their judgment.

## Core Product Thesis

The path to a credible recruiting and scouting platform begins with the people who generate the data: coaches and evaluators. If coaches trust Rostr enough to run their actual tryouts and seasons on it, the evaluations they enter become the foundation for verified athlete profiles that scouts and college programs can trust. The data must flow upstream from real operations, not be entered retroactively for marketing purposes.

**Data that comes from real workflows is trustworthy. Data entered for show is not.**

## Product Wedge

The wedge is the coach/evaluator operational workflow — specifically the tryout evaluation flow. This is a high-pain, low-tooling problem:

- Coaches currently use clipboards, Google Sheets, or memory
- Evaluation data gets lost, miscommunicated, or never digitized
- Multi-evaluator coordination is manual and error-prone
- Players and families get no standardized feedback

Rostr solves this by making evaluation entry fast enough for live tryouts, multi-evaluator capable, and automatically connected to player profiles.

Once a program runs tryouts on Rostr, the data naturally extends to roster management, practice planning, game-day operations, and player development — all workflows that depend on the same player and evaluation data.

## Technical Identity

Rostr is a **Vite + React 18 SPA** (not Next.js) using TypeScript, TailwindCSS, and Supabase (PostgreSQL + Auth + RLS + Edge Functions). It is deployed as a static build. The codebase uses a service layer pattern (`src/services/`) with `{ data, error }` return contracts and Zod validation on all critical mutation paths. State management is React Context (AuthContext, SessionContext) — React Query is installed but underutilized. The app is mobile-first with a max-width constraint (`max-w-lg`). There is no SSR, no server components, no API routes — all data flows through the Supabase JS client.

See ARCHITECTURE.md and KNOWN_ISSUES.md for detailed technical context.

## Current Build Phase

**UI Productization Sprint** — the core features work. The current objective is making the existing product feel polished, operationally trustworthy, and demo/pilot ready. This means: consistent visual language (section headings, card patterns, filter pills, empty states, loading skeletons), not new features.

## Long-Term Vision

### Layer 1 — Current Build Mandate

A polished, reliable coach-side MVP that can be used during real tryouts and season operations by a high school or club baseball program. This means:

- Tryout evaluation entry that works under field conditions (mobile, fast, reliable)
- Roster management with level assignments (Varsity / JV / Freshman)
- Practice planning with time blocks, coach assignments, and print capability
- Game scheduling with lineup building and printable lineup cards
- Player profiles with verified metrics and development trends
- A unified schedule view combining games and practices
- A command-center home page for daily coach use
- Demo-ready polish: skeletons, empty states, consistent visual language

### Layer 2 — Strategic Expansion Direction

- Multi-sport support (the architecture is sport-agnostic; baseball is the pilot sport)
- Scout and recruiting search (basic infrastructure exists: public profiles, search, comparison)
- Program analytics and season-over-season trends
- Parent/family portal for player visibility
- Club organization management (multi-team, multi-season)
- Athletic director dashboards

### Layer 3 — North Star Vision

A verified athlete identity layer for youth and amateur sports. Every athlete has a longitudinal performance record built from real program evaluations across seasons, sports, and organizations. College coaches, scouts, and recruiters can search and verify athlete data because it was generated by credentialed evaluators through actual program operations — not self-reported.

## Primary User Groups

1. **Head Coach / Program Admin** — Runs tryouts, manages rosters, plans practices, builds lineups, reviews rankings. The primary user whose daily workflow must be excellent.
2. **Assistant Coach / Evaluator** — Enters evaluation scores during tryouts and sessions. Needs a fast, focused scoring interface.
3. **Player** — Views their verified profile and development trends. Passive consumer of data generated by coaches.
4. **Scout / Recruiting Viewer** — Searches and compares player profiles. Depends on data credibility established by coach workflows.
5. **Athletic Director / Club Admin** — Oversees multiple teams and coaches within a program. Needs confidence that the system is organized and trustworthy.

## Core Product Principles

1. **Reliability over features** — A feature that works perfectly is worth ten that work partially. Never ship a workflow that fails under real conditions.
2. **Speed of data entry** — Evaluation entry must be fast enough for live tryouts. Every unnecessary tap or load time is a failure.
3. **Simple UX** — Coaches are not power users. Every screen should be immediately understandable. Prefer obvious over clever.
4. **Clear permissions** — Roles must be predictable. Coaches should never wonder who can see or edit what.
5. **Clean architecture** — Maintainable code over fast code. Service layers over inline queries. Types over guesses.
6. **Sport-agnostic design** — Nothing in the data model or core logic should be baseball-specific. Sport-specific details live in configuration, not schema.
7. **Targeted improvements** — Fix what's broken, polish what's rough, build what's missing. No unnecessary rewrites or speculative overbuilding.

## Near-Term Success Definition

The app can be handed to a real high school or club baseball coach who can:

1. Log in and see a useful home page
2. Import or add players
3. Configure evaluation metrics
4. Run a tryout session with live score entry
5. Review rankings and make roster decisions
6. Plan practices and schedule games
7. Build lineups and print lineup cards
8. Show a player their verified profile

All of the above must work on a phone, load quickly, and not lose data.

## Long-Term Success Definition

Multiple sports programs across different sports use Rostr for their operations. The evaluation data they generate powers a recruiting search platform where college coaches can find and verify athletes. The platform's credibility comes from the fact that every data point traces back to a real evaluation by a credentialed coach during an actual program event.

## Scope Discipline

Every feature decision must pass this test: **Does this make the coach's daily workflow better, or does it serve a user we haven't earned yet?**

Build for the coach first. The scout, the recruit, the athletic director — they benefit later, from the data the coach generates. If the coach doesn't trust the tool enough to use it, nothing downstream matters.

## Not Tonight's Scope Unless Assigned

The following are explicitly out of scope for the current build phase. They are valid future features but must not delay MVP polish or be speculatively built:

- College recruiting marketplace or scout matching
- Messaging or chat between users
- NIL tools or financial features
- Payment processing or subscription billing
- Advanced analytics or AI-powered insights
- Video upload or highlight reel integration
- Public recruiting search (beyond basic existing infrastructure)
- Social features, follows, or activity feeds
- Desktop/responsive redesign (mobile-first is the current target)
- Email delivery infrastructure (invitations, notifications)
- Multi-organization management
- Season-over-season historical analysis
- Third-party integrations (GameChanger, Hudl, MaxPreps)
